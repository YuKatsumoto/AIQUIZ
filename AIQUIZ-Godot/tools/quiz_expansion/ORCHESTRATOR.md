# クラウドセッション用 作問オーケストレーション手順

このファイルは、Claude Desktop から起動したクラウドセッションが読む指示書です。
あなた（このセッションのClaude）は**オーケストレーター**として、担当セッションIDの表にある
「教科×学年」をサブエージェントに作問させ、独立レビュー・検証・抜き取り確認・コミット・pushまで**最後まで自律的に**行います。
ユーザーへの質問で止まらないこと。

**目標は数ではなく品質**。1問の誤答が全体の信用を落とす。品質のために時間やトークンを多く使うのは構わない。
問題数が目標に少し届かなくても、基準に満たない問題を入れるよりよい（不足分は報告する）。

## 0. 準備

```
git fetch origin quiz-expansion/base
git checkout -b quiz-expansion/<セッションID小文字> origin/quiz-expansion/base   # 例: quiz-expansion/s1
```

`AIQUIZ-Godot/tools/quiz_expansion/SPEC.md` と `REVIEW.md` を全部読む。サブエージェントにも必ず読ませる。

## 2. 1つのセルの流れ（作問 → 検証 → 独立レビュー → 修正 → 抜き取り → push）

1つのセルの中の batch は**順番に**作る（b が push まで終わってから c。c は b と重複しないこと）。
セル同士は並列でよい。**同時に動くサブエージェントは最大3つ**。サブエージェントが使えない環境なら、
同じ手順を自分で順に行う（その場合もレビューは作問とは別の新しい気持ちで、ブラインド解答から行う）。

### 2.0 モデルの使い分け（クレジット節約）
サブエージェントを立ち上げるときは model を明示する（Agent/Task ツールの model 引数）:
- 作問サブエージェント: **sonnet**（出力量が最も多い工程。Opus の半額）
- 独立レビューサブエージェント: **opus**（品質の最終関門）
- オーケストレーター（このセッション）自身は、抜き取り検査と指示出しに集中し、シャード全体を読み込まない
  （抜き取りは `blind_review.py show <file> <開始> <終了>` で範囲を絞って表示する）。

### 2.1 作問サブエージェント
次のプロンプトを `{...}` を埋めて渡す:

```
小学生向けクイズゲームのオフライン問題を作る。作業ディレクトリはリポジトリのルート。
目標は数ではなく品質。SPEC.md §2 の品質基準を1問ずつ満たすこと。
1. AIQUIZ-Godot/tools/quiz_expansion/SPEC.md を全部読み、厳密に従う。
2. 担当: 教科 {教科}、{学年}年。ファイル {シャードパス}（batch "{batch}"、{問数}問）を作る。
3. 書き始める前に python AIQUIZ-Godot/tools/quiz_expansion/list_existing.py {教科} {学年} で既存問題の一覧を全部読む。
   offline_bank.json やシャードの JSON を丸ごと読まない。これらと同じ問題・言い換えだけの問題は作らない。
4. SPEC.md §5 の手順1〜4を行う（単元と問う知識の計画 → 作問 → 自己チェック → validate でエラー0・警告解消）。
5. git の commit/push はしない。shards/ の担当ファイル以外は変更しない。
{教科・学年ごとの注意（§3 から該当部分をそのまま貼る）}
最後に短く報告: 問数、単元と問数、validate の結果行、自己チェックで直した問題数、残った警告とその理由。
```

### 2.2 独立レビューサブエージェント（作問とは別の、新しいサブエージェント）
作問サブエージェントに続けてやらせない。必ず新しく立ち上げる。

```
小学生向けクイズ問題の独立レビュアーとして働く。作業ディレクトリはリポジトリのルート。
AIQUIZ-Godot/tools/quiz_expansion/REVIEW.md の手順どおりに、{シャードパス} を審査する（教科 {教科}、{学年}年）。
SPEC.md §2 も読むこと。正解キーを見る前に、blind_review.py show で全問をブラインドで解き、check で突き合わせる。
指摘を見つけたら、そのままシャードファイルを直してよい（直し方は SPEC.md §2 に従う）。
直した問題はもう一度ブラインドで解いて確認し、validate.py でエラー0を確認する。git の commit/push はしない。
最後に REVIEW.md の「レビュアーの報告」の形式で報告する。
```

### 2.3 オーケストレーターの最終確認
1. `python AIQUIZ-Godot/tools/quiz_expansion/validate.py <ファイル>` でエラー0、警告は誤検知のみであることを確認。
2. **抜き取り検査**: ランダムに20問を選び、自分で正解キーを見ずに解いてから突き合わせ、SPEC.md §2 の基準で審査する。
   1問でも誤り（REVIEW.md のチェック1・2・9）があれば直し、新しいレビューサブエージェントでファイル全体をもう一度レビューする。
3. そのシャードだけを `git add` → commit（例 `quiz: science g1 b (+191)`）→
   `git push -u origin quiz-expansion/<セッションID小文字>`。拒否されたら `claude/quiz-expansion-<セッションID小文字>` に push。
   シャードが1つ終わるたびに push して、途中で止まっても成果が残るようにする。
4. master には絶対に push しない。offline_bank.json や SPEC.md など他のファイルは変更しない。

## 3. 教科・学年ごとの注意

- **理科・社会の1・2年**: 学校では生活科にあたる。身近な自然（季節、草花・野菜の育ち方、虫・小動物、天気、
  水・風・音・光・ゴム・磁石で遊ぶ）や、身近な社会（家族と家の仕事、学校の人と施設、公共施設、町の店や
  働く人、交通安全、季節の行事、昔の遊び）から出す。ひらがな中心、1年生が読める短い文。
  「人によって答えが変わる」問題（好きなもの、家庭による習慣、マナーのうち正解が1つに決まらないもの）は禁止。
- **理科3〜6年**: 学習指導要領の単元どおり。観察・実験の結果予想や理由、条件制御の問題を入れる。
- **国語**: その学年までの配当漢字だけを使う。読み・書き・部首・ことわざ・慣用句・四字熟語（高学年）・
  敬語（高学年）・文法・言葉の意味・同音異義語など。例文の一部を答えさせる問題の
  「answer appears in the question」警告は誤検知として扱ってよい。
- **社会3〜6年**: 3年は市区町村のくらし・店・農家や工場・消防や警察、4年は都道府県・47都道府県の位置と特色・
  水やごみ・自然災害・伝統文化と先人、5年は国土・気候・農業水産業・工業・情報・環境、6年は政治・歴史・国際。
  年によって変わる統計や順位、現職の人物は出さない。
- **英語**: 小学校外国語の語彙と表現の範囲。4択は全部英語か全部日本語にそろえる。
  3・4年は外国語活動（あいさつ、数、色、形、曜日、天気、身の回りの物、好き嫌い）、
  5・6年は外国語（月・日付、時刻、教科、職業、できること、道案内、町の施設、過去の出来事、行きたい国、将来の夢）。
- **算数5・6年**: 計算は全問で検算する。文章題を3割以上。5年は小数・分数のかけ算わり算、倍数約数、
  合同、図形の角、面積、体積、単位量あたり、割合、平均、速さ。6年は分数のかけ算わり算、比、拡大縮図、
  円の面積、角柱円柱の体積、比例反比例、場合の数、資料の整理（代表値）、文字と式、対称な図形。

## 4. 最後に

全セル完了後、`python AIQUIZ-Godot/tools/quiz_expansion/validate.py` を担当ファイルすべてに対して実行し、
最終 push を確認して、次を短く報告する:
- push したブランチ名
- ファイルごとの問数と validate 結果
- 独立レビューのブラインド解答の不一致数・null 数と、直した内容の傾向
- 抜き取り検査で見つけて直した誤りの数と内容
- 目標に届かなかったセルがあればその数と理由

## 5. S9: 試験運用分の磨き直し

S9 は新しい問題を作らず、試験運用で作った次の4ファイル（各200問）を、現在の SPEC.md と REVIEW.md の基準で磨き直す:
`shards/science_g5_a.json`、`shards/japanese_g3_a.json`、`shards/social_g6_a.json`、`shards/english_g4_a.json`。

1. ファイルごとに §2.2 の独立レビューサブエージェントを立ち上げる（同時に最大3つ）。
2. あわせて validate.py の警告を解消する。特に:
   - 正解だけが長い・具体的な問題 → 誤答を正解と同じ長さ・具体性に書き直す。
   - 同じ型の問い方が8%を超える → 問い方を変える（SPEC.md §2.3）。
   - 薄い解説 → SPEC.md §2.4 の水準に書き直す。
   - `t >= 6.5` が3割未満 → 一部の易しい問題を、理由・比較・場面への当てはめ・順番などを問う問題に作り替える。
3. 問題数は200のまま保つ（削除したら同じ単元で差し替える）。ファイル名と batch は変えない。
4. §2.3 の最終確認をして、ファイルごとに commit・`quiz-expansion/s9` へ push する。
